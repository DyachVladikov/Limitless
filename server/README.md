# Limitless — бэкенд

Next.js API + TypeScript + PostgreSQL. Один владелец, вход по паролю без регистрации. Бэкенд работает с согласованными 18 таблицами: [структура БД](../docs/backend-redesign.md). Все запросы фронтенда описаны в [API.md](API.md).

Справочники и игровой контент автоматически не создаются. Пока БД пустая, списки пустые, выдача заданий сообщает об отсутствии подходящих записей. Профиль создаётся только явным `POST /api/profile` после входа. Уже применённую миграцию повторять не нужно; `replace-legacy.sql` повторно запускать нельзя — он удаляет данные.

## Локальный запуск

Нужен Node.js 22. Из каталога `server`:

```sh
npm ci
npm run hash-password
```

Последняя команда скрыто запрашивает пароль и подтверждение, печатает готовый хеш `scrypt:...`. Пароль — минимум 12 символов. Скопируй параметры из [.env.example](.env.example) в свой `server/.env`, сохранив файл локально, и заполни:

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | PostgreSQL URI из Supabase → Connect с паролем БД. Это **не** URL проекта и **не** publishable/service-role API key. |
| `OWNER_PASSWORD_HASH` | Результат `npm run hash-password` целиком. |
| `SESSION_SECRET` | Отдельная случайная строка не короче 32 байт. |
| `CRON_SECRET` | Другая случайная строка не короче 32 байт для планировщика. |
| `APP_ORIGINS` | Точные адреса фронтенда: например `http://localhost:5173`, в production `https://app.example.com`. Несколько — через запятую. Без путей и завершающего `/`. |
| `DATABASE_POOL_SIZE` | Размер пула на один процесс, по умолчанию 3. |
| `DATABASE_CA_CERT` | Необязательный PEM доверенного CA, если цепочка сертификата БД не входит в системное хранилище; допускаются литералы `\n`. |
| `SESSION_COOKIE_SAMESITE` | `lax` по умолчанию. `none` — только для фронтенда и API на разных сайтах с HTTPS. |

Каждый случайный секрет можно отдельно получить командой:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Строку подключения бери из панели Supabase целиком. Для постоянного сервера подходит direct connection; при сети только IPv4 — session pooler. Для serverless — transaction pooler. Спецсимволы пароля нужно URL-кодировать. Подробности: [официальная инструкция Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres).

Удалённое подключение проверяет TLS-сертификат. Если доверенного CA не хватает, укажи сертификат проекта через `DATABASE_CA_CERT`; проверка сертификата не отключается. Параметры TLS из URL не могут переопределить проверку в драйвере. См. [SSL в node-postgres](https://node-postgres.com/features/ssl).

```sh
npm run dev
```

API доступен по `http://localhost:8080/api`. `GET /api/health` проверяет доступность процесса; подключение к БД проверяется первым авторизованным игровым запросом. После входа вызови `POST /api/profile` с `{ "name": "Твоё имя" }`. Дальше при открытии приложения вызывай `POST /api/session/open`.

Старые `NEXT_PUBLIC_SUPABASE_*` серверу больше не нужны. Новые секреты никогда не добавляются в `VITE_*`, `NEXT_PUBLIC_*`, исходники фронтенда или git. Фронтенд работает только с HTTP API и cookie: `credentials: 'include'`. Для POST/PATCH/PUT/DELETE нужен `X-Requested-With: Limitless`.

## Публичное размещение

Из каталога `server`:

```sh
npm ci
npm run build
npm start
```

`npm start` слушает порт 8080; HTTPS обеспечивает хостинг или обратный прокси. Рекомендуется разместить фронтенд и API на одном сайте, например `app.example.com` и `api.example.com`: cookie `SameSite=Lax` работает без зависимости от разрешения сторонних cookie. Для разных сайтов нужен `SameSite=None; Secure`, но браузер может блокировать сторонние cookie даже при корректном CORS.

Задай production-переменные окружения на сервере, включая `APP_ORIGINS`. Без конфигурации защиты API закрыт. В production cookie имеет `HttpOnly`, `Secure`, префикс `__Host-` и срок 7 дней. Смена `OWNER_PASSWORD_HASH` или `SESSION_SECRET` отзывает все ранее выданные сессии. Выход удаляет cookie текущего браузера; серверного реестра сессий нет.

Вход ограничен 30 попытками за 5 минут и двумя одновременными вычислениями хеша на процесс. Для нескольких реплик/serverless добавь общий rate limit на `/api/auth/login` в хостинге или прокси. RLS таблиц оставь включённым: браузер не обращается к Supabase напрямую. Бэкенд использует серверное PostgreSQL-подключение из Connect.

## Смена дня

Игровой день начинается в 00:00 по Москве, то есть в 21:00 UTC. Настрой внешний планировщик на **POST**:

```http
POST https://api.example.com/api/jobs/rollover
Authorization: Bearer <CRON_SECRET>
```

Можно запускать каждые 15 минут (`*/15 * * * *`): повторный вызов безопасен. Только секрет планировщика, без cookie и без заголовка Origin. Планировщик с поддержкой только GET не подходит без адаптера.

Игровые запросы также догоняют пропущенные дни. Каждый активный день закрывается по своим правилам; длинное отсутствие вне запланированного отпуска может потребовать много запросов к БД, поэтому регулярный cron нужен и при закрытом приложении. Разворачивать многомесячное восстановление на платформе с коротким лимитом HTTP-запроса не стоит. Периоды запланированного отсутствия сохраняют стрики, не назначают задания и не штрафуют.

## Структура кода

```text
app/api/[...path]/route.ts   адаптер Next.js
api/router.ts               маршрутизация и общая транзакция
core/                      SQL, валидация, auth, HTTP, даты, сериализация
modules/game/              профиль, дейлики, квесты, XP, ранги, фокус, смена дня
modules/sections/          спорт, питание, учёба, книги, ситуации, LeetCode, менторы
config/balance.ts          версионированный игровой баланс
tests/                     проверки на временной PostgreSQL (PGlite)
supabase/redesign/         применённая схема, проверки SQL, инструкция миграции
```

Каждый игровой запрос использует одну транзакцию, транзакционный advisory lock и блокировку единственного профиля. Действие, XP, квесты и стрики либо фиксируются вместе, либо откатываются вместе. Параметризованные SQL-запросы выполняются на одном соединении, как требует [node-postgres для транзакций](https://node-postgres.com/features/transactions). Изменяемые записи защищены `version`; выдачи — отдельным ID назначения. Именованные prepared statements не используются.

Баланс находится в [config/balance.ts](config/balance.ts). Уже выданные задания и открытый день используют сохранённые снимки. Для изменения баланса добавляй новую версию с сохранением старой в `balanceFor`, чтобы старый открытый день мог корректно завершиться.

## Проверки

```sh
npm test
npm run test:db
npm run typecheck
npm run build
```

Тесты создают временную PostgreSQL в памяти из настоящей миграции и собственные фикстуры. Они не читают `server/.env`, не подключаются к Supabase и не наполняют настоящую БД. PGlite проверяет SQL, ограничения и откаты; нагрузка и конкуренция нескольких реальных сетевых соединений этим стендом не проверяются. Сборка не делает запросов к БД.
