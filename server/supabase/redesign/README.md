# Пустая база Limitless в Supabase

Этот каталог создаёт **18 таблиц без данных** по [согласованной схеме](../../../docs/backend-redesign.md). Включены все поля, семь внешних ключей, ограничения, индексы, автоматические версии записей и закрытый доступ. Профиль тоже остаётся пустым.

## Замена старой БД в текущем проекте

По выбранному варианту прежние данные Limitless удаляются, а новая пустая схема создаётся **в том же проекте Supabase**. Для этого готов один файл: **[replace-legacy.sql](replace-legacy.sql)**. Он уже содержит очистку и всю начальную миграцию; склеивать файлы или запускать их по частям не нужно.

1. Останови старый бэкенд на время перехода: его запросы несовместимы с новой схемой.
2. Открой SQL Editor нужного проекта Supabase от стандартной роли `postgres`.
3. Скопируй **весь `replace-legacy.sql`** в один запрос и выполни. После успешного завершения старые данные приложения удалены, вместо прежних таблиц созданы 18 новых пустых таблиц.
4. Выполни [verify.sql](verify.sql): 18 строк таблиц, везде `row_count = 0`, `rls_enabled = true`, клиентские права — `false`, серверные — `true`. Второй результат: `foreign_key_count = 7`.

Файл удаляет 15 таблиц прежнего приложения, их данные, индексы, ограничения, политики и триггеры, а также функции `handle_new_user()` / `handle_updated_at()`. Если сохранился старый триггер `auth.users.on_auth_user_created`, он тоже удаляется: он пытался бы создавать профиль прежнего формата.

Системные разделы Supabase, пользователи Auth, содержимое Storage, расширения и история Supabase CLI сохраняются. Скрипт не пересоздаёт проект и не удаляет схему `public` целиком. Это полная замена **прикладной БД Limitless из миграций 001–012**, а не сброс всей платформы Supabase.

Очистка и создание находятся **в одной транзакции**. При ошибке создание новой схемы и удаление старой откатываются вместе. Если SQL-клиент оставил транзакцию открытой, выполни `ROLLBACK` в том же соединении. Не продолжай выполнять остаток файла вручную. Успешный `COMMIT` завершает удаление старых данных; эта транзакция не является их резервной копией.

Если обнаружится неизвестная зависимость или оставшаяся прикладная таблица/представление/последовательность, скрипт откажет в замене. После установки новой схемы повторный запуск тоже отклоняется, чтобы не стереть новый прогресс. Для дальнейшего развития используются обычные новые миграции.

**После `replace-legacy.sql` не запускай начальную миграцию повторно и не запускай старые `001–012`.** Контент добавляется отдельно. Новый бэкенд уже работает с этой схемой; профиль создаётся через защищённый API. См. [запуск сервера](../../README.md) и [все маршруты](../../API.md).

## Если БД изначально пустая

[20261010000000_initial_schema.sql](migrations/20261010000000_initial_schema.sql) остаётся отдельным вариантом для чистого проекта. В нём нет удаления старых данных. Выполняется целиком вместо `replace-legacy.sql`, затем проверяется тем же `verify.sql`.

## Сборка файла замены

`replace-legacy.sql` — готовый файл для SQL Editor, сгенерированный из служебной части очистки и исходной начальной миграции. Он намеренно находится **вне `migrations/`**, чтобы автоматический запуск миграций не выполнял разрушительную замену.

Для разработки, из корня репозитория:

```sh
node server/supabase/redesign/scripts/build-replacement.mjs
node server/supabase/redesign/scripts/build-replacement.mjs --check
```

Правки схемы вносятся в источник, файл замены вручную не редактируется. После применения начальная миграция фиксируется и больше не переписывается; последующие изменения оформляются отдельными файлами.

## Что уже обеспечивает БД

- Единственный возможный профиль `id = 1`; отсутствие строки до настройки допустимо.
- Типы, обязательные поля, допустимые значения, неотрицательные показатели, согласованность состояний назначения и завершения.
- Форматы JSON из документа: расписания, снимки наград, счётчики, изображения, реплики и текущие уведомления.
- Одна текущая выдача LeetCode и одна попытка ситуации на весь соответствующий пул; законченная выдача остаётся текущей до замены.
- Семь связей с `ON DELETE RESTRICT`, одна отметка волейбола на дату; результаты упражнений разрешены только для зала. Тип посещения (`gym / volleyball`) фиксируется при создании, остальные данные можно исправлять. Удаление упражнения из состава программы не уничтожает историю.
- При вставке `version = 0`, `updated_at = created_at`. При обновлении триггер сохраняет `created_at`, увеличивает предыдущую `version` на один и ставит `updated_at = statement_timestamp()`.

Для защиты от старой команды текущий бэкенд проверяет `version` внутри общей транзакции под advisory lock и блокировкой единственного профиля. Все записи приложения должны проходить через этот API; само наличие столбца и триггера не запрещает ручной SQL обойти такую проверку. Для `focus_sessions`, `workouts`, `nutrition_entries` ID обязателен: клиент генерирует его один раз и повторяет при повторной отправке. У справочников UUID может сгенерировать БД; `profiles.id` и `mentors.id` задаются явно.

Миграция **не реализует игровой бэкенд**: начисление/отмену XP, общий двухчасовой лимит фокуса за день, выбор пяти дейликов, кулдауны, автоматическое завершение квестов, расписание обработки полуночи, показ менторов и API. Эти операции реализованы транзакционно в `server/modules` и общем API; планировщик настраивается отдельно по [инструкции сервера](../../README.md). Например, отметка `completed_at` сама по себе не начисляет опыт, а запись `current_day` не запускает планировщик. Стартовый баланс хранится в `server/config/balance.ts`.

## Доступ

У всех таблиц включён RLS. Роли `anon` и `authenticated` не имеют прав на таблицы; открытых политик нет. `service_role` получает только чтение и изменение данных (`SELECT / INSERT / UPDATE / DELETE`). Технические функции находятся в `limitless_private`; не добавляй эту схему в список Exposed schemas Data API.

Доступ к действующему API ограничен сессией владельца. При использовании Supabase Data API секрет `service_role` должен храниться только на сервере, без префикса `NEXT_PUBLIC_`; текущая реализация использует PostgreSQL напрямую через серверный `DATABASE_URL`. [Документация Supabase о RLS и серверной роли](https://supabase.com/docs/guides/database/postgres/row-level-security).

Старый `server/lib/supabase.ts` удалён. Текущий `server/core/database.ts` использует `pg` и одно соединение на транзакцию; публичный anon-ключ для него не нужен.

## Наполнение и последующие изменения

Да, данные добавим позже. Профиль, задачи, квесты, блюда, упражнения и реплики можно загрузить отдельным SQL-файлом наполнения или миграцией данных. Повторяемое наполнение должно использовать стабильные ID и явно определённое поведение при конфликте, чтобы не сбросить текущий прогресс.

Новые поля, ограничения и связи добавляем **новыми миграциями**, например `20261011000000_add_...sql`. Уже применённый начальный файл не редактируем и не запускаем заново. Изменения сначала проверяем на временной БД; миграции с изменением существующих данных предваряем резервной копией.

Сейчас предусмотрен ручной запуск SQL Editor. Он **не регистрирует файл в истории Supabase CLI**; файл замены также не очищает старую историю CLI, если она существует. Если позже перейдём на CLI, создадим отдельный каталог проекта CLI только с новыми миграциями и сверим историю; уже выполненную `20261010000000` отметим применённой после проверки схемы. Не направляй `supabase db push` на старый каталог миграций. Supabase описывает это в разделах [миграции и их история](https://supabase.com/docs/guides/deployment/database-migrations) и [отдельное наполнение БД](https://supabase.com/docs/guides/local-development/seeding-your-database).

## Локальная проверка SQL

Тесты используют PostgreSQL в PGlite, создают временные БД в памяти и тестовые роли Supabase. Они не читают `.env`, не подключаются к Supabase и не добавляют данные в рабочую БД. Зависимость устанавливается отдельно от приложения:

```sh
npm install --prefix /tmp/limitless-db-test --no-audit --no-fund --ignore-scripts @electric-sql/pglite@0.3.14
PGLITE_MODULE=/tmp/limitless-db-test/node_modules/@electric-sql/pglite/dist/index.js node --test server/supabase/redesign/tests/*.test.mjs
```

Команды выполняются из корня репозитория. PGlite проверяет исполнение PostgreSQL SQL, ограничения, триггеры и права. Тест замены предварительно применяет настоящие старые миграции, добавляет данные и проверяет как успешный переход, так и восстановление старых данных при ошибке. Это не проверка размещённого Supabase, PostgREST или параллельных запросов API.
