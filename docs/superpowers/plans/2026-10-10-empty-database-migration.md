# Пустая БД для редизайна бэкенда

Основание: [согласованная схема](../../backend-redesign.md), 18 таблиц и 7 внешних ключей. Пользователь разрешил подготовку файлов, но не применение к Supabase, удаление прежней БД или коммит.

## План

1. Проверить конфликты со старыми миграциями. Подготовить независимый набор в `server/supabase/redesign/`, без запуска `001–012` и без переноса старых данных.
2. Написать исполняемые проверки PostgreSQL: пустая установка, ограничения состояний, JSON, связи, версии, доступ ролей и защита существующей схемы. До реализации убедиться, что проверка наличия согласованной схемы падает.
3. Создать одну атомарную начальную миграцию: предварительные проверки, технические функции, все 18 таблиц, ограничения, индексы, триггеры версий, RLS и права серверной роли. Не добавлять ни одной строки данных.
4. Выполнить проверки на временной локальной БД. Провести независимый обзор SQL и устранить существенные замечания.
5. Написать инструкцию для нового проекта Supabase, проверку результата и порядок будущего наполнения/изменения схемы. Согласовать описание автоматических `updated_at`/`version` с документацией.

## Границы

- Старая БД, старые миграции и приложение остаются на месте. Новая начальная миграция отклоняет установку поверх существующих прикладных таблиц.
- Профиль тоже пустой: его строка появится при последующем наполнении.
- Не реализуются API, расчёты XP, баланс, выдача дейликов, смена дня и фоновые задания. Их транзакции разрабатываются следующим этапом.
- Доступ к личным данным — через будущий защищённый бэкенд; `anon`/`authenticated` не получают доступ к таблицам. Секрет серверной роли не предназначен для фронтенда.
- Необходимые изменения позже оформляются новыми миграциями, справочники — отдельным наполнением. Уже применённая начальная миграция не переписывается.

## Проверка и обзор

Проверить все 18 пустых таблиц и семь FK, корректные и некорректные состояния назначения/завершения, отсутствие обхода CHECK через NULL/JSON null/NaN, одну текущую попытку, отсутствие результатов у волейбола, сохранение истории при правке программы, автоматическую версию, блокировку клиентских ролей. Отдельно проверить атомарность ошибки и повторного запуска, сохранность старых объектов. Локальные проверки не подменяют применение к удалённому Supabase: оно остаётся за пользователем.

## Результат выполнения

Все пять шагов выполнены 10 октября 2026 года. Подготовлена одна начальная миграция, инструкция, запрос проверки и исполняемые тесты. Старые SQL-файлы не изменены, удалённая БД не затронута, коммит не создан.

- Начальная проверка до реализации упала ожидаемо: найдено 0 таблиц вместо 18.
- После независимого обзора исправлены конечность дат/времени, проверка пустых реплик и конкурентная смена типа посещения; тесты сначала воспроизвели ошибки, затем прошли. Добавлен индекс непросмотренных завершённых квестов.
- Техническое решение: тип посещения фиксируется при вставке, чтобы связь результатов с залом оставалась корректной при разных уровнях изоляции. Исправление ошибочного типа требует пересоздания записи без зависимых результатов; остальные исправления доступны. Решение отражено в спецификации.
- Финальный запуск: `PGLITE_MODULE=/private/tmp/limitless-db-test/node_modules/@electric-sql/pglite/dist/index.js node --test server/supabase/redesign/tests/schema.test.mjs` — **28/28**, без пропусков, код 0.
- Отдельное выполнение `verify.sql` на свежей БД — 18 пустых таблиц, семь FK, ожидаемые права и RLS. Движок PostgreSQL 17.5 в PGlite; размещённый Supabase и параллельные подключения не тестировались.
- `git diff --check` — без ошибок. Изменения интерфейса и API в работу не входили.

## Дополнение: замена прежней БД в том же проекте

После подготовки начальной миграции пользователь явно разрешил отказаться от старых данных и запросил один SQL-файл для их удаления и создания новой схемы. Это заменяет первоначальную рекомендацию сохранить старую БД; удалённый запуск и коммит по-прежнему не выполняются агентом.

- Создан `server/supabase/redesign/replace-legacy.sql`: одна транзакция, удаление 15 известных старых таблиц и двух функций, снятие старого триггера регистрации, неизменённое тело начальной миграции.
- Генератор `scripts/build-replacement.mjs` собирает файл из источников, `--check` проверяет его актуальность. Разрушительный файл находится вне каталога автоматических миграций.
- Защита повторного запуска сохраняет уже установленную новую схему. Неизвестные зависимости останавливают замену. Системные разделы Supabase и их данные сохраняются.
- Начальная проверка замены упала ожидаемо: старые 15 таблиц вместо новых 18. Затем семь тестов замены прошли на настоящих старых SQL-файлах с заполненными таблицами, включая откат при поздней ошибке.
- Финальная проверка двух наборов: **35/35**, без пропусков; сборка актуальна, независимый обзор не выявил блокирующих замечаний.
